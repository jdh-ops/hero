# hero 기획 문서

> 핵앤슬래시 + 파밍 + 빌드 조합 장르의 **간소화된 싱글 웹 게임**.
> 장르와 시스템 구조는 참고하되, 세계관·이름·아트·수치는 모두 직접 만든다.

마지막 정리: 2026-11-12

---

## 1. 확정된 결정

| 항목 | 결정 |
|---|---|
| 플레이 방식 | **싱글 플레이** (거래 없음 → "거래 재화"는 상점/교환소 화폐로 대체) |
| 플랫폼 | **웹** (PC + 모바일 브라우저), PWA로 홈 화면 설치 지원 |
| 그래픽 | **2D** |
| 목표 | 최대한 가볍게: 첫 로딩 **5MB 이하**, 이후 오프라인 플레이 가능 |
| 배포 | GitHub Pages (`jdh-ops/hero`) |
| 저장 | 로컬 우선 + Supabase 클라우드 동기화 (아래 6장) |

| 엔진 | **Phaser 3** (확정) |
| 직업 | 여러 직업을 넣을 계획. **첫 구현은 전사, 마법사 2개** |
| 세계관 | 아직 정하지 않음 (직업 추가에 방해되지 않게 열어 둠) |

### 기술 스택

```
TypeScript + Vite + Phaser 3
→ GitHub Pages 배포 + PWA
```

- Phaser 3: 2D 웹 게임 엔진, 충돌·애니메이션·입력·카메라·사운드 내장 (약 1MB)
- 순수 Canvas는 위 기능을 모두 직접 만들어야 해서 제외

## 2. 게임 영역

| # | 영역 | 내용 | 메모 |
|---|---|---|---|
| 1 | 캐릭터 | 스탯, 데미지 공식, 레벨 | **모든 영역의 공통 언어. 가장 먼저 확정** |
| 2 | 스킬 | 액티브, 패시브, 보조 젬 | 스킬 **태그 체계**(투사체, 범위, 원소, 지속 등)를 먼저 정해야 보조 젬 설계 가능 |
| 3 | 특성 | 레벨업 포인트 사용 | 큰 트리 대신 노드 수십 개 규모의 작은 보드 |
| 4 | 장비 | 강화 방식, 옵션 테이블 | 옵션은 1번 스탯 목록 재사용. 슬롯 수, 등급, 옵션 개수 규칙 정의 |
| 5 | 던전 | 난이도, 몬스터, 드랍 테이블 | 난이도 → 몬스터 레벨 / 옵션 / 드랍 품질 연결 |
| 6 | 경제 | 강화 재료, 맵 입장 재료, 상점 화폐 | 재화별 **소스(획득처)와 싱크(소모처)** 정리 |
| 7 | 전투 & 파밍 | 핵심 루프 | 영역이라기보다 게임 그 자체. **가장 먼저 프로토타입** |
| 8 | 증명의 장 | 보스, 성장 체감 | 보스 + DPS 측정 허수아비 + 무한 층 도전 등 |

### 추가로 필요한 영역

- 인벤토리 / 창고 / UI (툴팁, 장비 비교, 정렬, 루팅 필터)
- 저장 데이터 구조
- 데이터 테이블 (스킬·옵션·몬스터·드랍을 JSON으로 관리, 코드와 분리)
- 밸런싱 시트 (레벨별 몬스터 체력 vs 플레이어 기대 DPS 곡선)

## 3. 개발 순서

```
0단계  결정: 싱글/웹/2D ✅, 엔진 Phaser 3 ✅, 목표 플레이 시간(보류)
1단계  스탯 사전 + 데미지 공식 + 태그 체계 → docs/스탯과_데미지.md (초안)
2단계  전투 프로토타입: 이동, 기본공격, 스킬 1개, 몬스터 1종
3단계  드랍 → 장비 착용 → 스탯 반영 (파밍 루프 완성)
4단계  스킬 확장 + 보조 젬
5단계  던전 난이도 단계 + 드랍 테이블
6단계  특성, 강화, 경제 조율
7단계  보스 / 증명의 장
```

> 핵심: 2~3단계에서 **"때리고 → 줍고 → 끼고 → 더 세진다"** 루프를 최대한 빨리 완성해서 재미를 검증한다.

## 4. 간소화 범위 (첫 버전)

- 직업 **2개** (전사, 마법사), 직업당 스킬 4~6개
- 장비 슬롯 4~6개 (무기, 방어구, 장신구)
- 데미지 타입 4종 (물리, 화염, 냉기, 번개), 능력치 3종 (힘, 민첩, 지능)
- 재화 3~4종 이내
- 던전: 맵 1종 + 난이도 숫자

---

## 5. 모바일 방침

- **조작**: 왼쪽 가상 조이스틱 + 오른쪽 스킬 버튼 3~4개, 기본공격 자동
- **화면**: 가로 고정 권장
- **성능**: 화면 내 몬스터 수 상한, 오브젝트 풀링, 이펙트 단순화
- **세션 길이**: 맵 1판 3~5분
- **용량**: 그래픽은 도형/아이콘/작은 스프라이트 위주, 효과음은 최소한으로

## 6. 저장 방침

### 6.1 로컬 + 클라우드

```
로컬 저장   : 변화 있을 때마다 (localStorage / IndexedDB)
서버 저장   : 1~5분 주기 + 아래 이벤트 시점
  - 맵 클리어 / 보스 처치 / 장비 강화
  - 앱이 백그라운드로 갈 때 (visibilitychange)
  - 변경 없으면 전송 생략
```

- 세이브 형식에 처음부터 **버전 번호**와 **저장 시각**을 포함
- **세이브 코드 내보내기/불러오기**(텍스트 백업) 제공
- iPhone Safari는 설치하지 않은 사이트의 저장 데이터를 지울 수 있음 → PWA 설치 유도
- 여러 기기 충돌: 저장 시각 기준 최신 우선 (필요하면 선택 UI)

### 6.2 Supabase (potion과 같은 프로젝트, 같은 방식)

potion이 쓰는 Supabase 프로젝트를 함께 쓰고, **로그인 방식도 potion과 같게** 간다.

potion 방식 요약 (`potion/supabase/game.sql`, `potion/js/cloud.js`):

- Supabase의 로그인 기능(**Auth)은 쓰지 않음**. 닉네임 + 비밀번호로 직접 만든 계정
- 비밀번호는 bcrypt 해시만 저장, 로그인하면 세션 토큰 발급
- 표는 브라우저에서 직접 못 읽음. `security definer` 함수(`game_sign_in`, `game_save` 등)로만 본인 데이터에 접근
- 브라우저에는 **Project URL + anon 키만** 둠
- 7일 미접속 계정 자동 삭제

hero 적용 방식: **B. 계정 분리로 확정** (2026-11-12)

| 방법 | 내용 | 장단점 |
|---|---|---|
| A. 계정 공유 | potion의 `players`/`player_sessions`를 그대로 쓰고, 세이브만 `hero_saves` + `hero_load`/`hero_save` 함수 추가 | 한 계정으로 두 게임. 단 potion의 **7일 미접속 삭제**가 hero 세이브까지 지움 → 삭제 기준을 두 게임 접속 합산으로 바꿔야 함 |
| **B. 계정 분리 ✅ 확정** | `hero_players`, `hero_sessions`, `hero_saves`와 `hero_*` 함수를 따로 만듦 (potion SQL 복사 후 이름만 변경) | potion에 영향 없음. 나중에 별도 프로젝트로 옮기기 쉬움. 계정은 게임마다 따로 |

주의사항:

- 이름은 모두 `hero_` 접두어로 분리
- Supabase Auth를 안 쓰므로 Auth 설정·URL Configuration은 건드릴 필요 없음
- **service_role / secret 키는 절대 게임 코드에 넣지 않음**
- 무료 한도(DB 500MB 등)는 두 게임이 나눠 씀. 1주일간 요청이 없으면 프로젝트가 일시 정지될 수 있음

### 6.3 진행 순서

1. 로컬 저장 + 세이브 코드 백업으로 개발 시작
2. 게임 루프가 재미있다는 게 확인되면 Supabase 동기화 추가
